# Style Selection

Choose a suitable visual direction with meaningful variety. No style or level is the default.
Use only the conversation and supplied artifacts as preference/history evidence; do not invent
cross-session memory. Explicit style, brand, reference, or series continuity takes priority.

## Decide whether to ask

- **Specific direction or current-series revision:** honour it; do not repeat a style question.
  A local content edit keeps the current style. If a direction conflicts with medium limits or
  readability, explain and offer a compatible adaptation.
- **First canvas with no established direction:** offer 2–3 concrete suitable styles and an
  “agent chooses” option in the user's language. Each option needs its name, a visual difference,
  and why it fits. Broad words such as “professional”, “clean”, or “technical” filter the options;
  they do not identify a template. Use selectable choices if available, otherwise one compact
  question. Combine missing purpose and style in one question when useful. Once asked, wait for a
  submitted answer before rendering; silence and preselection are not a choice.
- **Delegated choice, no-questions request, or noninteractive run:** select and generate directly.
  Do not ask again just because no template was named. A previous “choose for me” applies only
  within its stated scope; it does not authorize every future choice.
- **Established preference in the current conversation:** for a similar independent task, reuse
  the accepted preference as a constraint, not necessarily the same template. Proceed without a
  new question when the user has established a default or delegated that scope. An acceptance of
  one canvas alone is not a standing preference. Ask only if a changed audience, medium, or purpose
  creates a meaningful unresolved choice; keep previous explicit delegation in scope.
- **Explicit alternatives or “another style”:** select distinct suitable directions and produce
  only the number of complete outputs requested. If no count is given for “another”, make one.

## Shortlist by fit, then difference

Read the full [catalogue](../CATALOG.md) and [comparison profiles](../STYLE_PROFILES.md) once per
selection context. Reuse them during the conversation; do not reload all 35 design files.

1. Identify actual constraints: audience, mood, brand/palette, label load, text contrast, intended
   size, and medium limits. Decide the content's relationships and likely structure independently
   of the preview. A technical subject does not require a particular aesthetic.
2. Build a suitable pool across all levels. Reject directions whose defining traits conflict with
   the brief; an open poster with minimal labels is not an equal substitute for a dense system map.
   `unspecified` profile values are uncertainty, not evidence of universal fit. If no catalogue
   palette satisfies a strict brand, disclose a brand-adapted direction rather than claiming an
   unchanged template; preserve the brand and topology. Under no-questions delegation, make the
   nearest compatible adaptation directly and state the deviation; otherwise surface the choice.
3. From that pool choose 2–3 candidates that differ in more than accent colour. Compare geometry /
   stroke, type hierarchy, depth, rhythm / density, and palette. Prefer differences on two or more
   visible dimensions when compatible. Do not force different levels or families into the shortlist
   at the expense of fit. If only one direction fits, explain the narrower choice rather than
   padding it with incompatible options.
4. Use available recent outputs to favour an equally suitable different visual character for new
   independent canvases. Compare both profile dimensions and family; a new slug alone is not
   variety. Preserve explicit series continuity and accepted brand constraints.
5. Show the candidates with bundled `assets/styles/<slug>.png` previews when the host supports it.
   Label them as style examples, not proposed layouts. Do not reuse a fixed example trio, the
   README showcase, alphabetical ordering, or the first row as an implicit recommendation.

## Automatic choice

Apply the same fit/diversity shortlist internally. Prefer the strongest fit; use recent similarity
as a tie-break, never a blanket penalty against the best-suited style. With no history and no clear
winner, a runtime random tie-break among the suitable candidates can reduce deterministic reuse;
otherwise make a deliberate choice with a concrete reason. Do not claim a diversity guarantee.

Announce the selected style and its reason, with an available alternative briefly. This is not an
extra approval step. Then read its `templates/<slug>/design.md`. Profile summaries do not override
the full design. If a newly discovered design constraint invalidates the choice, reselect; ask again
only if it creates an unresolved user preference, not for ordinary implementation decisions.

## Preserve information; vary visual language

Read previews as references for palette, shape treatment, hierarchy, and rhythm. Never inherit
their example content, column count, stage count, or aspect ratio. Choose structure from the real
content's causality, time, hierarchy, comparison, or feedback relationships.

Apply density, scale, stroke, corners, depth, spacing, and accents within the selected design and
native editable primitives. For “another style”, aim for differences on at least two dimensions
beyond colour when suitable. A process must remain a process; do not change its topology merely to
look different. If strict brand/medium constraints limit the contrast, say so rather than breaking
them. Inspect both legibility and actual visual differences after conversion, not only SVG colours.
