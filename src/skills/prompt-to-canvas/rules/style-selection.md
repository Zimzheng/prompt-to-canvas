# Visual direction

## Autonomy and explicit choices

When no style is specified, choose and build without a style question. "Professional", "clean", or
"technical" describe intent; they do not name a template. Ask only for an unresolved requirement
that materially changes the artifact, or when the user asks to choose among previews. If a question
has actually been asked, wait for its answer; elapsed time is not approval.

Explicit style, brand, reference and series continuity take precedence. A local content edit keeps
the current visual system. A request for another style produces a new direction while preserving
facts and relationships. Use only the supplied conversation/artifacts for history; do not claim
cross-session memory or write preference logs without a request.

## Fit first, meaningful variation second

1. Decide reading context, label load, relationship complexity, intended size and emphasis before
   aesthetics. A technical topic does not imply blue, a grid, or a restrained level.
2. Use the full [catalogue](../CATALOG.md) and relevant [profiles](../STYLE_PROFILES.md) to identify
   suitable directions. Compare a few plausible candidates on hierarchy, spacing, geometry,
   strokes, depth and palette. Do not always start with the first row, README showcase or a fixed trio.
3. Choose the strongest fit. When several fit equally, consider a visibly different direction from
   recent independent outputs in this conversation. Do not randomize into an unsuitable style,
   impose quotas, or sacrifice consistency in a requested series. No style or level is the fallback.
4. If catalogue constraints do not serve the content, use a **custom** or **brand-adapted** direction.
   Define paper/ink, semantic accents, text scale, stroke hierarchy, corners and spacing in a short
   working note. Keep these decisions coherent across the artifact. Custom means intentional design,
   not a mixture of unrelated template signatures. Do not claim an adapted style is unchanged.
5. Read the chosen full design guide. A few candidate guides may be inspected to resolve a real
   uncertainty; do not load all 35. If a design conflicts with topology or readability, reselect or
   disclose an adaptation. Historical renderer restrictions defer to current [RULES.md](../RULES.md).
6. Announce the chosen direction with a content-specific reason, then continue building. Show
   candidate previews only when the user requests a choice or alternatives.

## Variation has more than one axis

Composition belongs to content, while visual treatment can vary independently. "Another style"
should alter suitable dimensions beyond colour (for example, line hierarchy and typography scale,
figure/ground and corner treatment, or spacing and emphasis). It must not delete a feedback edge
or change causality. A new slug alone is not evidence of visual diversity.

For a genuinely different interpretation requested by the user, composition can also change: a
system may be explained by responsibility boundaries or by execution sequence. Preserve its facts
and make the changed reading purpose clear. More variants are not required for an ordinary request.
